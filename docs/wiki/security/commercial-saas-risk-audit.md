# 商业 SaaS 外联、可追踪面与许可证审计

> 审计日期：2026-07-28
>
> 适用范围：当前仓库源码、Windows 桌面运行时、公开介绍站、发布脚本与依赖清单
>
> 说明：本文是产品和工程风险清单，不替代律师出具的正式法律意见。

## 结论

当前 Windows EXE 运行时没有发现向原作者发送数据的遥测、分析、崩溃上报、远程日志或硬编码原作者 API。代码中的 `telemetry` 主要用于本地内存统计、本地 SQLite 用量记录和本地日志，不会自动上传。

已经发现并清理的外联残留包括：

- 公开介绍站硬编码的原作者 GitHub Pages 地址、站点路径、canonical、社交分享地址、sitemap 与 robots 地址。
- 一个未被使用、但启用后会访问第三方 GitHub 代理的星标查询模块。
- Pull Request 模板中指向原作者仓库 CLA 的链接。
- 公开站发布工作流中的旧站点包名错误；发布前新增遗留外联检查。

这些清理减少了非必要外联，但**不能解决商业授权问题，也不能用于掩盖代码来源**。`LICENSE` 和 `NOTICE` 中的原作者版权及许可证声明必须保留，除非取得权利人明确书面授权后由律师确认可以如何调整。

## 原作者是否能“追踪到我们”

需要把四种情况分开：

| 情况 | 是否会在用户运行 EXE 时通知原作者 | 处理 |
|---|---|---|
| 本地 Git `upstream` 指向原仓库 | 否；Git 配置不进入 EXE，当前 push 已禁用 | 保留为来源和差异参考，不向其推送 |
| `LICENSE` / `NOTICE` 中保留作者信息 | 否；纯本地文本，没有网络请求 | 必须保留，不能当作追踪代码删除 |
| 访问原作者网站、更新源、统计或崩溃上报端点 | 会向对应服务器暴露常规网络信息 | 原作者公开站残留已移除；未发现遥测和崩溃上传 |
| 对外发布相似产品、源码或安装包 | 不是代码追踪，但可能被公开渠道、用户或权利人发现 | 不能以“不可被发现”为目标，必须先完成授权与合规 |

## 当前运行时外联清单

### 产品必需

| 外联 | 默认状态 | 数据范围 | 商业版规则 |
|---|---|---|---|
| 自有中转站 | 尚待接入 | 登录 Token、模型请求、用量、充值与必要业务字段 | 正式 C 端所有 AI 请求只走自有中转；使用 HTTPS；明确隐私、留存、日志脱敏和故障重试规则 |
| 自有桌面更新站 | 仅打包时显式配置才启用 | IP、应用版本、更新通道及下载请求 | 只接受 `OXNOVEL_DESKTOP_UPDATE_URL` 生成的自有通用更新源；无配置保持关闭 |
| 自有公开介绍站 | 仅发布时显式配置 | 普通网站访问日志 | 使用 `OXNOVEL_PUBLIC_SITE_URL`；无配置不生成 canonical、绝对 sitemap 或原项目地址 |

### 当前存在但 C 端默认不应开放

| 能力 | 当前代码行为 | 风险 | C 端处理 |
|---|---|---|---|
| 内置模型供应商直连 | 可访问 DeepSeek、SiliconFlow、OpenAI、Anthropic、xAI、Kimi、MiniMax、智谱、DashScope、Google 等地址 | 绕过自有计费与隐私边界，用户内容直接发给第三方 | 正式 C 端删除入口并由本机服务拒绝；不提供专家模式或运行时恢复开关 |
| 自定义 Provider | 用户可填写任意 API URL | 远程部署时存在 SSRF、内网探测和数据外发风险 | 正式 C 端删除入口并拒绝自定义地址；旧能力仅允许存在于构建时隔离的内部开发包 |
| 钉钉 / 企微 Webhook | 未配置时关闭，配置后发送导演跟进内容 | 可能把作品名、任务状态和摘要发到外部频道 | C 端默认移除或隐藏；启用时逐项说明发送内容 |
| Qdrant、Reranker、S3 | 按配置连接本机或外部服务 | 外部存储和检索服务可能接触作品数据 | 本地模式默认关闭；云端部署使用自有服务与网络白名单 |
| 图片、TTS、视频服务 | 按配置访问生成端点，也可拉取外部图片 | 内容外发、任意 URL 拉取和 SSRF | C 端第一阶段不开放；后续经代理、白名单和文件类型/大小校验接入 |

### 已确认不属于远程追踪

- `memoryTelemetry`：只输出到本地进程日志。
- Prompt 质量统计：只保存在当前进程内存。
- 导演 LLM 用量：只写本地数据库，用于成本与熔断。
- 桌面日志：只写本地日志目录，启动失败时由用户主动打开或复制路径。
- npm / pnpm 依赖下载：只发生在开发或构建阶段，不是最终用户启动 EXE 的运行时上报。

## 许可证与商业授权：P0 阻断项

仓库的 `LICENSE` 和 `NOTICE` 明确声明：

- 默认许可证为 `AGPL-3.0-only`。
- 将项目或修改版作为 SaaS、托管或类似服务的核心，需要项目维护者另行商业授权。
- 原始版权归属仍写为 `ExplosiveCoderflome and contributors`。

因此，在取得书面授权或律师确认可行的开源履约路径之前，不能把“删除作者地址”视为获得了闭源商业化权利。至少需要在以下路线中明确选择一种：

1. **商业授权路线**：与原权利人签署书面商业许可，明确覆盖桌面客户端、本地后端、自有中转 SaaS、修改、打包、收费、更新、品牌与再分发。
2. **AGPL 路线**：按 AGPL 要求提供对应源码、许可证、修改说明和网络用户获取源码的入口；由于当前仓库又附带了“服务型商用需另行授权”的声明，正式上线前仍应让律师确认两部分文本的关系。
3. **洁净重写路线**：只保留由法律审查确认不受保护的需求和产品思想，由未接触原实现的团队重新设计代码、提示词、测试与素材；不能只是重命名、删链接或大规模改 UI。

在路线确认前：

- 不删除或改写 `LICENSE` / `NOTICE`。
- 不把原作者姓名、来源记录或提交历史当作“追踪器”清理。
- 不接受新的外部代码贡献进入商业主线；自有 CLA 必须先明确签约主体和商业再许可权。
- 不公开宣称已经拥有闭源 SaaS 商业授权。

还需要核实权利主体链条：`NOTICE` 使用的是 `ExplosiveCoderflome and contributors`，Git 历史和当前仓库账号使用了其他名称或邮箱，README 也记录过外部贡献者。若当前经营者就是原维护者，应保存能够证明同一主体和代码权利归属的材料；若不是，应由实际版权人和需要参与授权的贡献者签署文件，不能只依赖仓库管理员权限、一次 fork 或 PR 模板复选框。

GNU 官方对 AGPL 的说明指出：如果修改后的程序在服务器上与用户交互，服务器应向这些用户提供正在运行版本的对应源码。参考：[GNU 为什么使用 Affero GPL](https://www.gnu.org/licenses/why-affero-gpl.zh-cn.html)。

## 已实施的持续保护

- 新增 `pnpm audit:commercial-egress`，检查客户端、桌面端、服务端、公开站和发布配置，阻止原作者公开站、原 CLA 链接和第三方 GitHub 星标代理重新进入可发布代码。
- 公开站默认使用根路径，不再默认部署到原项目 Pages 路径。
- 只有显式设置 `OXNOVEL_PUBLIC_SITE_URL` 时，才生成绝对 canonical、sitemap 和 robots 中的站点地址。
- 站点、正式桌面版和测试桌面版发布工作流都在构建前运行外联残留检查。
- 原项目标识仍允许出现在 `LICENSE`、`NOTICE`、历史来源说明和“阻止旧更新源进入安装包”的安全检查中，因为这些位置不会产生网络请求。

## 商业上线前的执行门槛

### P0：没有完成就不能收费上线

- [ ] 取得商业授权，或由律师书面确认 AGPL 履约上线方案。
- [ ] 核实 `NOTICE`、Git 作者、仓库账号和历史贡献者的权利链，保存可审计的授权与 CLA 证据。
- [ ] 明确商业主体、商标和产品名称的可用性。
- [ ] 中转站注册、Token、余额、充值、退款和幂等契约完成并通过联调。
- [ ] 隐私政策明确作品正文、提示词、账号、支付与日志会经过哪些服务、保存多久、如何删除。
- [ ] EXE 完成代码签名，更新元数据与安装包签名验证通过。
- [ ] 正式 C 端只能访问本地服务、自有中转和自有更新站，所有 AI 能力只能经过自有中转。

### P1：公开测试前完成

- [ ] 为桌面本地 API 增加每次安装随机生成的本机访问凭据，避免其他网页或本机进程直接调用创作接口。
- [ ] 为服务端外部请求建立统一出口层和域名白名单，禁止私网、环回、链路本地和非 HTTP(S) 自定义目标。
- [ ] 正式 C 端删除自定义 Provider、内置供应商直连和专家直连入口，并由本机服务拒绝绕过中转。
- [ ] 关闭或隐藏钉钉、企微、S3、外部 Qdrant、TTS 和视频等第一阶段不开放的 B 端入口。
- [ ] 生成第三方依赖清单、许可证清单与发布物 SBOM。
- [ ] 日志默认脱敏，不记录完整 Token、密码、充值凭据和完整作品正文。
- [ ] 建立账号注销、本地数据删除、导出、备份和退款处理流程。

## 下一步建议

商业化风险的优先顺序不是继续删除名字，而是：

```text
先确认商业授权
-> 固定 C 端唯一外联边界
-> 完成登录 / 充值 / 中转闭环
-> 完成隐私、签名与更新安全
-> 再进入大规模 UI 和工作台改造
```
